# ADR-006 — Port the PA6 saga to a Temporal workflow with activity-level retry classification

**Status:** accepted
**Date:** 2026-11-01

## Context

In PA6, if the orchestrator died mid-saga, whatever it had in memory about
which steps had completed was gone. I tested this: made shipping slow,
killed `pa6-orchestrator` mid-call, checked `pa6/orchestrator/data/`
afterward — the idempotency record was stuck where it died, no way for a
retry to know payment had already succeeded.

Porting meant giving up direct control over retries. In PA6 I wrote the
retry loop myself; here `proxyActivities`'s `retry` block does it, and I
picked the policy values instead of the logic.

The other real decision: where "may this be retried?" gets decided. A
`4xx` from a mock (e.g. `payment_declined`) is a business refusal that
will be identical on a second try, so it becomes
`ApplicationFailure.nonRetryable`. Anything else (no response, a `5xx`) is
worth another attempt, so `.retryable`. Test 5 checks a refused payment is
attempted only once — a plain `Error` for a `4xx` would have let Temporal
retry it three times before failing.

I also killed the worker myself while shipping was mid-call, and watched
it in the Temporal UI. Payment stayed authorized exactly once; shipping
was called twice — once before the kill, once after restart, since the
in-flight attempt was lost and Temporal reran it not knowing the mock had
already received it: "at least once, not exactly once." If
`authorizePayment` had run twice instead of shipping, the customer would
be charged twice.

## Decision

`post()` in `activities/index.ts` classifies every failure: it inspects
`err.response.status`, throwing `ApplicationFailure.nonRetryable(message,
code)` for any `4xx`, or `.retryable(message, code)` for anything else.
All six activities call this one function, so the classification exists
once.

`checkout()` runs the four steps in sequence through a shared `runStep()`
helper, which records a `TraceItem` for success or failure. On failure it
stops and compensates whatever already succeeded, newest first: a failed
`reserveInventory` only refunds payment; a failed `createShipment` or
`sendNotification` releases inventory then refunds payment. Inventory is
never compensated when payment itself failed — nothing happened yet to
undo.

The retry policy on `proxyActivities` uses exactly the README's values:
`maximumAttempts: 3`, `initialInterval: "200 ms"`, `backoffCoefficient: 2`,
plus the given `startToCloseTimeout: "2500 ms"`.

`classify()` reads the caught `ActivityFailure` and decides whether it was
a `TimeoutFailure` (status `"timeout"`) or an `ApplicationFailure` (status
`"failed"`, `type` as the code). No exception escapes `checkout()` — every
path returns a `CheckoutResult` instead.

The amount is summed in cents, not floats: `toCents()` parses each
`unitPrice` string, multiplies by quantity, adds as integers, and
formats to a two-digit string once — same reason PA1 and PA4 kept money
as strings.

## Alternatives considered

I considered throwing a plain `Error` from every activity and letting
Temporal's default retry behavior handle everything. Rejected: a declined
payment would then be retried up to three times before the workflow saw it
fail — wasted time, and the wrong call count for test 5.

I also considered throwing on a business failure instead of always
returning a `CheckoutResult`. Rejected: the api only turns a
`CheckoutResult` into an HTTP response — a thrown workflow error becomes
`500 workflow_failed`, not the `422`/`504` the tests expect.

## Consequences

Every HTTP call is now an activity, so the workflow has almost no logic
beyond sequencing and trace-building — business behavior lives in two
places instead of one big function like PA6's orchestrator. Easier to
read, but a bug in `classify()` would mislabel every step's trace entry
the same wrong way, since every step routes through it.

A fifth step needs a new activity plus a new call-and-compensation branch
inside `checkout()` — sequencing is still hand-written, not data-driven,
so porting to Temporal didn't remove that repetition from PA6.

## What the engine took over

- The in-progress idempotency record PA6 wrote to disk before every saga
  and had to read back on restart — Temporal's workflow history is now
  that record, automatically, per `workflowId`.
- The retry loop and per-attempt timeout PA6's orchestrator wrote by hand
  around every downstream call — now declared once as a policy on
  `proxyActivities`, not re-implemented per call.
- Knowing "where was I?" after a crash — PA6 lost this the moment the
  orchestrator process died mid-saga; Temporal replays the workflow from
  its recorded history and continues from the exact step it was on.
