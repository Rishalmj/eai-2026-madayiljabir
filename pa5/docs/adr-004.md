# ADR-004 — Header-based correlation, file-backed idempotency, three-attempt retry

**Status:** accepted
**Date:** 2026-10-18

## Context

The first thing that tripped me up was `properties.headers` versus AMQP's
own `properties.correlationId`. I started by putting the id on
`properties.correlationId` because the name matched, then realized
`getRetryCount` and `withoutRetryHistory` in `shared/rabbit.ts` both read
from `msg.properties.headers`, not from that native field. If I'd kept it
on `properties.correlationId`, my own retry-counting code would never have
seen it. So the id had to move into `headers.correlationId` to actually
work with the code I was given, not just because a doc said so.

The second thing was watching test 6 (notification idempotency) pass and
actually reading my own log while it ran. The same order arrived at
`notifications.queue` twice, and the second delivery hit my duplicate check
before it ever reached `JSON.parse`. I ack'd it and returned without
touching `notification.log` or `results.notification`. That's the exact
moment the file-based check earned its place over an in-memory one — a
`Set` would have worked identically in that one test run, but only because
the container never restarted mid-test.

The third was retry counting. `getRetryCount` filters `x-death` entries to
`reason: "rejected"` only, because one retry cycle dead-letters a message
twice (once out of the consumer queue, once out of the retry queue). I
almost summed every `x-death` entry when I was reading the file, which
would have doubled my count and dead-lettered messages after their second
real failure, not their third.

## Decision

`payment-service`, `inventory-service` and `notification-service` each
declare `orders.dlq.exchange` → `orders.dlq` and `orders.invalid.exchange`
→ `orders.invalid` on startup, with identical fanout/durable properties, so
it doesn't matter which container starts first.

`order-service`'s `POST /orders` handler generates the correlation id with
`crypto.randomUUID()` and puts it only in `headers.correlationId` on the
published message — never on the order body, since
`additionalProperties: false` in the canonical schema would reject an
extra field.

Each consumer's callback checks the error it caught: `err instanceof
SyntaxError` means the body couldn't be parsed, which I classify as
permanent — republish to `orders.invalid.exchange` with the original bytes
and headers, ack, done. Anything else is temporary and falls into the
provided retry block, which checks `getRetryCount(msg) >= MAX_RETRIES - 1`
before deciding between another `nack(msg, false, false)` or a publish to
`orders.dlq.exchange`.

`notification-service` treats "processed" as "this correlationId is in
`processedIds`, loaded from `/data/processed-ids.json` by
`loadProcessedIds()` at startup and written back by `persistProcessedIds()`
after every new order." The check runs before `JSON.parse`, so a duplicate
never touches the log file at all.

`order-service`'s `/dlq/replay` drains `orders.dlq` one message at a time
with `channel.get`, reads the `originQueue` header each consumer set when
it dead-lettered the message, and republishes to `orders.return.exchange`
using that queue name as the routing key — so only the consumer that
failed it sees it again. It calls `withoutRetryHistory()` on the headers
first, which drops `x-death`, so the replayed message starts its three
attempts over instead of going straight back to the DLQ on its next
failure.

## Alternatives considered

I considered keeping the idempotency check as a plain in-memory `Set`,
since it's less code and test 6 would still pass. I rejected it because
the assignment specifically restarts the picture around durability — a
`Set` resets to empty on `docker compose restart notification-service`,
so a redelivered message after a real restart would be treated as new and
logged twice. The file costs a bit more code (load on startup, write on
every new id) but survives exactly the failure the assignment is testing
for.

## Consequences

Replay is now easy — `/dlq/replay` fixes any dead-lettered message by
routing it back to its own queue. But if a consumer downstream of me ever
forwards this message without keeping `headers.correlationId` intact, my
correlation tracing breaks silently — nothing throws, the id is just gone
from the next hop's logs. I also accepted a real limitation: if inventory
is down for longer than three retry cycles, its item lands in `orders.dlq`
and nothing tells payment or notification that it happened — an order can
show "paid" and "notified" while its inventory step is quietly sitting in
the DLQ until someone replays it.
