# ADR-000 — Ingest the legacy order export by slicing fixed-width columns and decoding as CP1257

**Status:** accepted
**Date:** 2026-09-13

## Context

The order file looked like plain text but was not. Reading it with
`readFileSync(path, "utf8")` did not throw an error — it just quietly turned
names like "Bērziņš" into garbled characters, because the file is actually
encoded in CP1257 (`windows-1257`), not UTF-8. Nothing crashed, so this would
have shipped silently if I hadn't checked the output by eye.

The amount field used a comma as the decimal separator (e.g. `45,20`).
Converting this with `parseFloat` after swapping the comma would still lose
information: `45,20` becomes `45.2` as a number, dropping the trailing zero,
and `7800,00` becomes `7800`. For money, that difference matters.

Line 6 of the order file was truncated — only 26 characters instead of the
expected 77. If I sliced this line by fixed column positions without checking
its length first, the fields would be sliced from the wrong place entirely, or
the program would produce a record with garbage or empty fields instead of
failing loudly.

The customer master file (`customers.csv`) was a separate file, in a
different encoding (UTF-8) from the order file, and included at least one
customer id that never appeared on any order.

## Decision

I implemented `decodeOrderFile(bytes)` using `TextDecoder("windows-1257")` to
turn the raw bytes into correctly-decoded text before doing anything else with
it — decoding happens once, up front, rather than trusting Node's default
UTF-8 read.

I implemented `toIsoDate(ddmmyyyy)` as pure string manipulation: splitting the
`DD.MM.YYYY` string on `.` and reassembling it as `YYYY-MM-DD`, with no call to
`Date` at any point, so there is no timezone or locale ambiguity.

I implemented `toDecimalString(amount)` to only ever manipulate the value as a
string — trimming it and replacing the comma with a period — and never
convert it to a JavaScript `number`. The `Order.amount` field is typed as
`string` for exactly this reason.

In `ingest()`, each line is checked against `ORDER_LINE_LENGTH` (77) before any
field is sliced from it. Lines that don't match are pushed into `rejected`
with their 1-based line number and a plain-language reason, and the loop
continues to the next line rather than throwing or silently skipping it.
Negative amounts are kept as ordinary orders — refunds are not filtered out.

Unmatched customers are found by collecting every `customerId` seen on an
accepted order into a `Set`, then checking every id from the customer CSV
against that set.

## Alternatives considered

I considered adding a small dependency like `iconv-lite` to handle the
encoding instead of using the built-in `TextDecoder`. I rejected this because
the assignment explicitly disallows encoding dependencies, and `TextDecoder`
already supports the `"windows-1257"` label natively in Node — there was
nothing the dependency would have given me that the standard library didn't
already provide.

I also considered storing `amount` as a JavaScript `number` and formatting it
back to a fixed 2-decimal string only when writing the report. I rejected this
because a number can still be produced correctly and then lose precision or
trailing zeros somewhere later in the pipeline before it's formatted — keeping
it as a string from the moment it's parsed removes that entire class of bug,
even if it means the caller can't do arithmetic on it directly without
converting first.

## Consequences

Rejecting malformed lines instead of throwing means the program is now
resilient to bad records, but it also means a systematic problem — for
example, if the entire file arrived corrupted, or the layout shifted by even
one character — would show up as a large `rejected` array rather than a hard
failure. Right now nothing alerts a human when `rejected` is unexpectedly
large; in a production version I'd want a threshold that raises an alert if,
say, more than 5% of lines are rejected in one run.

If the upstream system ever adds a new field in the middle of the record, or a
customer name is ever longer than 32 characters and gets truncated by the
source system itself, this code has no way to detect that — it would simply
read the wrong columns as if they were correct, silently, which is exactly the
kind of bug this assignment was built to teach me to notice. A longer-lived
version of this integration would ideally ask the upstream system for a
self-describing format (CSV with a header, or JSON) instead of a fixed-width
export, precisely so that a field being added or reordered doesn't silently
corrupt every row that comes after it.
