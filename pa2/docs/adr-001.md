# ADR-001 — Use a durable queue with publisher confirms and manual consumer ack for order messages

**Status:** accepted
**Date:** 2026-09-17

## Context

Four separate failure modes had to be handled, and each one only becomes
visible once you actually kill a container, not by reading the code.

Publishing messages with `X-Publish-Mode: fire-and-forget` (no confirms, no
persistent flag) and then running `docker restart pa2-rabbitmq` caused those
messages to vanish from the queue entirely, even though the HTTP client had
already received a `202` response for every one of them. This is the exact
scenario `04-publisher-confirms-prevents-loss.test.ts` checks for: a `202`
from a fire-and-forget publish does not actually promise the message is
safe, it only promises RabbitMQ accepted the TCP write.

Declaring the queue without `durable: true` would mean the queue itself
disappears on a broker restart, not just its messages — I confirmed this is
what `assertQueue(queueName, { durable: true })` in both `producer.ts` and
`consumer.ts` protects against, since both sides must declare the queue with
matching durability or `assertQueue` throws a channel error.

For the consumer side, if it acknowledges a message before finishing the
write to `received.jsonl`, a crash between the ack and the write loses the
message permanently — RabbitMQ has already deleted it from the queue,
believing it was delivered successfully, with no record of it anywhere. The
opposite order (write, then ack) is what `03-consumer-stopped-accumulates.test.ts`
relies on: because unacknowledged messages stay in the queue, stopping the
consumer entirely just makes the queue depth rise, with zero loss once it's
restarted.

Finally, the correlationId has to travel through three different places: the
`X-Correlation-Id` HTTP header (or generated if absent), the AMQP message's
own `correlationId` property (not the JSON body), and finally the
`correlationId` field written to each line of `received.jsonl`. Putting it
inside the JSON payload instead of the AMQP property would work for the
happy path but would silently break the moment `amqplib`'s tooling (or the
management UI) needs to correlate a message without deserializing its body.

## Decision

`connectProducerChannel` opens an AMQP connection, creates a **confirm
channel** (`createConfirmChannel()`, not a plain channel), and calls
`channel.assertQueue(queueName, { durable: true })` before returning it —
the queue itself is created durable up front, on the producing side.

`publishMessage` behaves differently depending on `options.mode`:
- In `"confirmed"` mode (the default), it calls `channel.sendToQueue` with
  `persistent: true` set on the message, and wraps the call in a `Promise`
  that only resolves once the confirm callback fires — meaning the function
  does not return, and the HTTP handler does not send `202`, until RabbitMQ
  has actually confirmed receipt.
- In `"fire-and-forget"` mode, it calls the same `sendToQueue` without
  `persistent: true` and without waiting for any callback — the function
  returns as soon as the call is made, regardless of whether RabbitMQ has
  processed it yet.

`connectConsumerChannel` opens a plain channel (not a confirm channel — the
consumer doesn't publish), declares the same durable queue with the same
name and durability flags as the producer, and sets `channel.prefetch(1)` so
RabbitMQ only hands this consumer one unacknowledged message at a time.

`handleMessage` reads `msg.properties.correlationId` (the AMQP property, not
anything from the JSON body), parses the message content as JSON, appends
one line containing the `correlationId`, a `receivedAt` timestamp, and the
payload to `received.jsonl` using `appendFileSync`, and only calls
`channel.ack(msg)` after that `appendFileSync` call has returned
successfully. The ack physically cannot happen before the write, because
it's the next statement in the same synchronous sequence.

## Alternatives considered

I considered acking the message immediately upon receipt, before writing to
`received.jsonl`, to reduce the window where a redelivery could happen after
a crash mid-write. I rejected this because it inverts the actual risk: a
crash between "ack" and "write" would delete the message from RabbitMQ with
nothing ever recorded, which is unrecoverable, whereas a crash between
"write" and "ack" only causes a harmless redelivery and a possible duplicate
line in `received.jsonl` — a problem that's at least detectable and
recoverable, unlike silent data loss.

I also considered keeping the default `guest`/`guest` RabbitMQ credentials
instead of the named `eai`/`eai-pa2` user already set up in
`docker-compose.yml`. I didn't change this configuration, but it's worth
naming: RabbitMQ's `guest` user is restricted to loopback connections by
default, and the management API calls the test suite makes from outside the
container (via the `15673` port mapping) would not be treated as loopback
from RabbitMQ's perspective — so `guest`/`guest` would work for AMQP
publishing but silently fail for anything hitting the management API from
the host.

## Consequences

Manual ack with `prefetch(1)` means this consumer processes messages one at
a time and cannot batch or parallelize deliveries — if the consumer is slow,
the queue backs up (which is actually the desired, safe behavior for this
assignment), but it also means throughput is capped by how fast a single
`appendFileSync` call plus JSON parsing can run, with no concurrency to fall
back on.

If two consumer instances were run against the same queue at once, RabbitMQ
would round-robin deliver messages between them rather than each instance
seeing every message — for `received.jsonl` specifically, that would mean
each instance appends to its own local file, splitting the record across two
files with no single source of truth, which the current setup doesn't
account for or detect.

Using `appendFileSync` (a blocking, synchronous write) inside `handleMessage`
means the consumer's event loop is blocked for the duration of each write.
For small JSON lines this is negligible, but if a message's JSON body were
very large (tens of megabytes), this synchronous write would noticeably
stall message processing — an async file write with the ack moved into its
completion callback would scale better, at the cost of slightly more complex
error handling.
