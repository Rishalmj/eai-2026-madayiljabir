# ADR-003 — Translate all three order sources through a shared enrichItems() helper, keyed on normalized PROD-XXX ids

**Status:** accepted
**Date:** 2026-09-24

## Context

Each of the three order files fought back in its own specific way.

The B2B file declares `encoding="windows-1257"` in its own XML prolog, and
reading its bytes as plain UTF-8 text turns the Latvian letters in the
customer's name and address into broken characters, with nothing throwing
an error — I only caught this by actually printing the parsed customer name
and seeing it come out wrong.

The three sources also don't agree on what a product id even looks like:
web already sends `PROD-001`, mobile sends a bare number like `001`, and the
B2B XML sends `SKU-PROD-001`. None of these can be sent straight to the
pricing API — it only recognizes the `PROD-XXX` shape.

The pricing API itself is the other thing that bit me: on a `200` it hands
back a JSON number for the price (e.g. `4.5`), and if I had just called
`String()` on that number I'd have gotten `"4.5"` instead of the required
`"4.50"` — exactly the same lost-trailing-zero problem as PA1's `amount`
field, just showing up again here with prices instead of order totals.

Lastly, every one of the three sources carries payment data in a different
spot: `customer.payment` (web), three separate top-level fields `pm`/`pan`/
`pexp` (mobile), and a `PaymentDetails` element sitting inside
`BuyerParty` (B2B). None of these have anywhere to go in
`../canonical/order.schema.json`.

## Decision

`normalizeProductId(source, rawId)` handles the three id formats: web is
returned unchanged, mobile gets `PROD-` prepended, and B2B has its `SKU-`
prefix stripped off with `.replace(/^SKU-/, "")`. All three translators call
this before ever touching the pricing API, so the API itself only ever sees
one consistent id shape.

`toDecimalAmount(price)` is a single line: `price.toFixed(2)`. This is the
only place a price number gets formatted, and it's called exactly once per
line item, right after the pricing API's response comes back — the number
is never round-tripped through a string and back to a number anywhere else
in the file.

`enrichFromPricing()` and `enrichItems()` are shared by all three
translators — I didn't write three separate pricing-lookup functions, one
per source. Each translator only builds a plain list of
`{ productId, productName, quantity }` in its own source's shape, then
hands that list to the same `enrichItems()`. A `404` from the pricing API
becomes an `UNKNOWN_PRODUCT` warning and that line item is dropped from
`items`; any other non-2xx response (I specifically tested this against a
`500`) becomes a `PRICING_API_ERROR` warning, also dropping just that one
item rather than failing the whole order. If every item in an order fails
this way, `translateWeb`/`translateMobile`/`translateB2B` return
`{ order: null, warnings }` instead of an order with an empty `items` array,
since the schema requires at least one item.

Payment data is filtered out simply by never reading it — none of the three
translators ever assigns `raw.customer.payment`, `raw.pm`/`raw.pan`/
`raw.pexp`, or the B2B `PaymentDetails` element to anything on the
`CanonicalOrder` I build. The filter isn't a separate "strip payment" step;
it's the absence of a mapping.

For an unrecognized currency code or B2B status string, I chose not to
throw: `mapCurrencyCode` passes an unknown numeric code through as a plain
string, and `mapB2BStatus`/`mapMobileStatus` fall back to `"new"` for
anything they don't recognize, rather than crashing the whole translation
over one field.

## Alternatives considered

I considered writing three separate enrichment functions, one per source,
since each source's raw item shape is different. I didn't do this because
the actual pricing lookup and warning-generation logic is identical once
the product id is normalized — duplicating it three times would just mean
fixing the same `toFixed(2)` bug in three places if I ever found it wrong,
instead of one.

I also considered failing the entire order the moment a single line item
comes back `404` from the pricing API, instead of dropping just that item
and continuing with the rest. I rejected this because a legitimate 5-item
order where one product happens to be temporarily out of the pricing
catalog would then produce nothing at all, instead of 4 correctly priced
items and one clear warning explaining exactly what was skipped and why.

For the unrecognized-currency-code case specifically, I considered throwing
an error instead of passing the numeric code through as a string. I chose
not to, mainly because I don't actually know what a real accounting or
finance system downstream would want to happen here, and silently
defaulting to a guess (like always falling back to EUR) felt like it could
hide a real data problem. Passing the raw code through at least makes the
oddity visible instead of pretending everything is fine.

## Consequences

Because `enrichItems()` calls the pricing API once per line item, in
sequence, an order with a lot of items would make that many sequential HTTP
calls before returning — for the 2-item fixtures here it's fine, but for an
order with, say, 50 items, this would be noticeably slower than it needs to
be. A production version would probably batch these calls or run them in
parallel.

If the canonical schema gains a new required field next semester, none of
these three translators would produce it, and every one of them would start
failing schema validation identically — there's no default or fallback
value being generated anywhere, so the failure would at least be loud and
consistent across all three sources rather than silently wrong in one.

Falling back to `"new"` for an unrecognized B2B status string is a real
risk I accepted: if the partner's system ever sends a status this course's
fixtures never showed me, my code would silently mislabel it as a brand-new
order instead of surfacing an error — which is convenient for keeping the
pipeline running, but means a genuinely wrong status could go unnoticed
rather than being flagged.
