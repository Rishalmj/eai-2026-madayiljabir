# ADR-003 — Translate all three order sources through a shared enrichItems() helper, keyed on normalized PROD-XXX ids

**Status:** accepted
**Date:** 2026-09-24

## Context

The B2B file declares `encoding="windows-1257"` in its own XML prolog.
Reading its bytes as UTF-8 turned the Latvian letters in the customer's
name into broken characters (`Bērziņa` became `B?rzi?a`), with no error
thrown — I only caught this by printing the parsed customer name.

The three sources also disagree on product id shape: web sends `PROD-001`,
mobile sends a bare `001`, B2B sends `SKU-PROD-001`. None of these can go
straight to the pricing API, which only accepts `PROD-XXX`.

`fast-xml-parser` gave back a single object for `<LineItem>` when the XML
had exactly one, and an array when it had more than one — I had to
normalize this to an array before iterating, or the single-item case would
have crashed or silently processed only part of an order.

The pricing API returns a JSON number for the price (e.g. `4.5`). Calling
`String()` on that gives `"4.5"`, not the required `"4.50"` — the same
lost-trailing-zero problem as PA1's `amount` field. Testing against
product `PROD-013` (unit price `4.5` in the catalog) confirmed this.

Every source keeps payment data somewhere different: `customer.payment`
(web), top-level `pm`/`pan`/`pexp` (mobile), and a `PaymentDetails` element
inside `BuyerParty` (B2B) — none of which have anywhere to go in
`../canonical/order.schema.json`.

## Decision

`normalizeProductId(source, rawId)` handles the three id formats: web
unchanged, mobile gets `PROD-` prepended, B2B has its `SKU-` prefix
stripped with `.replace(/^SKU-/, "")`.

`toDecimalAmount(price)` is `price.toFixed(2)` — the only place a price
number gets formatted, called once per item right after the pricing API
responds.

`enrichFromPricing()` and `enrichItems()` are shared by all three
translators, rather than three separate pricing-lookup functions. Each
translator only builds a plain `{ productId, productName, quantity }` list
in its own shape, then hands it to the same `enrichItems()`. A `404`
becomes an `UNKNOWN_PRODUCT` warning and drops that one item; any other
non-2xx (tested against a `500`) becomes a `PRICING_API_ERROR` warning,
also dropping just that item, never falling back to a price of `0.00`. If
every item in an order fails this way, the translator returns
`{ order: null, warnings }` instead of an order with an empty items array.

Payment data is filtered by never reading it — none of the three
translators assign `raw.customer.payment`, `pm`/`pan`/`pexp`, or the B2B
`PaymentDetails` element to the `CanonicalOrder`. The filter is an absence
of mapping, not a separate strip step.

For an unrecognized currency code or B2B status string, I chose not to
throw: `mapCurrencyCode` passes an unknown numeric code through as a
string; `mapMobileStatus`/`mapB2BStatus` fall back to `"new"` rather than
crashing the whole translation over one field.

## Alternatives considered

I considered three separate enrichment functions, one per source, since
each raw item shape differs. I rejected this because the pricing lookup
and warning logic is identical once the id is normalized — duplicating it
would mean fixing the same `toFixed(2)` bug in three places instead of
one.

I considered failing the entire order on a single `404`, instead of
dropping just that item. I rejected this because a 5-item order with one
temporarily unpriced product would then produce nothing, instead of 4
correctly priced items and one clear warning.

For the unrecognized-currency case, I considered throwing instead of
passing the raw code through. I chose not to, since I don't know what a
real downstream finance system would want, and silently defaulting to a
guess (e.g. always EUR) felt like it could hide a real data problem more
than surfacing the raw value does.

## Consequences

`enrichItems()` calls the pricing API once per item, in sequence. For the
2-item fixtures here this is fine, but a 50-item order would make 50
sequential HTTP calls before returning — noticeably slower than batching
or parallel calls would be.

If the canonical schema gains a new required field next semester, none of
the three translators would produce it, and all three would fail schema
validation identically — loud and consistent, rather than silently wrong
in just one source.

Falling back to `"new"` for an unrecognized B2B status string is a cost I
accepted: if the partner ever sends a status this course's fixtures never
showed me, my code would silently mislabel it as brand-new instead of
raising an error — convenient for keeping the pipeline running, but a
genuinely wrong status could go unnoticed.
