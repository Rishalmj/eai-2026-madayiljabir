# ADR-005 — Strict sequencing, header-classified failures, file-backed idempotency

**Status:** accepted
**Date:** 2026-10-25

## Context

The first decision came from `callStep`. Axios throws on a timeout and on a
downstream 422 the same way — both are just a caught exception. I check
`err.code === "ECONNABORTED"` (set when axios's own `timeout` option fires)
versus `err.response` actually existing (a real reply, just a bad one).
Without that check, a slow-but-alive payment service and an actually
declining one look identical, and the assignment wants `504` for one and
`422` for the other.

The second was compensation for shipping and notification. Neither mock
exposes a rollback route. So when shipping fails, the code still has to walk
backward through whatever *did* complete — payment and inventory — even
though the step that just failed has nothing of its own to undo. My first
draft tried to "compensate shipping" and there was nothing to call.

The third was the idempotency race. I write `state: "in_progress"` before
any downstream call, so a second request with the same key that arrives
mid-saga reads that state and gets `409 idempotency_conflict` instead of the
saga running twice. That only works because the check and the write happen
with no `await` in between — an async check first would let two requests
both pass before either one wrote anything.

## Decision

`callStep(stepName, url, body, timeoutMs)` makes one downstream POST and
always returns a result — success, failed, or timeout — never throwing. It
classifies the axios error using the `ECONNABORTED` check above, and it also
records `startedAt`/`finishedAt`/`durationMs`, which is what ends up in the
trace.

`runSaga` calls payment, inventory, shipping, notification in that fixed
order, one `await` after another, never `Promise.all`. On any non-success
result, it calls `compensate(orderId, completedUndoableSteps, trace)`, which
walks the finished undoable steps in reverse — inventory before payment —
and calls `inventory/release` then `payment/refund`. If either compensation
call doesn't come back `success`, the saga reports `status: "failed"`,
`code: "compensation_failed"`, `422` — the original failure reason is
dropped, because a checkout where the refund also failed is worse than the
original decline.

`POST /checkout` reads the stored idempotency record before doing anything
else. Same key + same payload hash + a finished record → I return that
exact stored `httpStatus` and `response` again, and `runSaga` never runs.
Same key + `in_progress` → `409 idempotency_conflict`. Same key + different
hash → `409 idempotency_payload_mismatch` (already in the scaffold).

## Alternatives considered

I considered calling shipping and notification in parallel with each other,
since neither depends on the other's result. I didn't do it. The
assignment's hidden tests check step order by timestamp, and running two
steps at once makes "the order they ran in" ambiguous — which one do I put
first in the trace if they finish within a millisecond of each other?
Sequential is slower but the trace stays honest.

I also compared this to PA5, where the same order went out as one event and
payment, inventory and notification each reacted independently. That
choreography had no single place enforcing "payment before inventory" —
each service just picked the message up when it arrived. Checkout can't
work that way: inventory must not run if payment declined, and only one
place — this orchestrator — sees all four outcomes at once to decide on
compensation.

## Consequences

Adding a fifth downstream step means editing `runSaga` in three places: the
new `callStep` call, the undoable-steps list if it has a rollback, and
`compensate`'s reverse-walk. Nothing generic reads that list from
configuration — it's hardcoded step by step, fine at four, repetitive at
eight.

The idempotency store is one JSON file with no locking. Two *different*
keys racing for the same `orderId` can both read the file, both finish
their own saga, and the second write wins — the first saga still ran and
charged the customer, but its result never makes it into what the second
write saw. I accepted this because the tests never send two different keys
for one order at once; a real system would need a per-order lock, not just
synchronous file writes.

If the orchestrator is killed between writing `in_progress` and finishing
the saga, that key is stuck at `in_progress` forever — no timeout clears it,
so every future retry with that key gets `idempotency_conflict` and never a
real answer.
