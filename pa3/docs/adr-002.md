# ADR-002 — Track order results in a dictionary keyed by item index, with an idle timeout for missing workers

**Status:** accepted
**Date:** 2026-09-23

## Context

When I split one order into separate items, each item goes off to a
different queue and gets processed on its own. The problem is: how does
anything later know which items belonged to the same order, and how does
it know when it has everything it needs?

I also had to think about what happens when a worker just doesn't answer.
If I wait forever for a missing item, the order never finishes and nobody
downstream ever finds out something is wrong.

Two other things I had to think through: what if the same result message
shows up twice (this can genuinely happen with RabbitMQ if a worker is
slow to acknowledge), and what if two different orders are being
processed at the same time — I didn't want their results getting mixed
together by accident.

## Decision

I kept the `orderId` and `correlationId` the same value on every single
item message that comes out of the splitter, and I never let any worker
touch or rewrite that field. That's the thread that ties everything back
together later.

For tracking progress, I used one dictionary called `in_flight`, where
each key is an `orderId`. Inside that, I store the results I've gotten so
far in another dictionary, keyed by `itemIndex` this time (not just a
counter). Using `itemIndex` as the key means if the exact same result
comes in twice, it just overwrites the same spot instead of counting as
two separate items — so duplicates can't accidentally inflate the count.

For the timeout, I went with 5 seconds for this assignment, since that's
what the test setup expects. In a real system, I'd want this to be based
on how long the slowest normal worker actually takes, plus some safety
margin — maybe based on watching real timings for a week and picking
something like double the slowest observed time. The important part is
that my timeout resets every time a new result comes in for that order
(I update a `lastActivity` timestamp on every result), rather than being a
fixed countdown from when the order first arrived. That way, a big order
that's still making genuine progress doesn't get cut off early just
because it has more items to wait for.

When an order does time out, I don't just say "it's incomplete" — I list
exactly which item numbers never showed up (`missingItemIndexes`), so
whoever reads that message later knows precisely what to retry instead of
having to guess or redo the whole order.

I also used a lock (`threading.Lock`) around any place where I read or
change the shared `in_flight` dictionary, so two orders being processed at
the same moment can't interfere with each other's data.

## Alternatives considered

I thought about using a fixed timer instead of an idle one — like, "give
up exactly 10 seconds after the order first arrived, no matter what." I
didn't go with this because a bigger order (say, 50 items) would just need
more time naturally, even if every worker is healthy and still actively
working through it. A fixed timer would unfairly cut that order off, even
though nothing is actually broken.

I also thought about not bothering with a lock at all, since for this
assignment there usually aren't many orders running at the exact same
time. I decided against skipping it, because without the lock, two orders
arriving at almost the same moment could end up reading and writing the
same dictionary at once, and in Python that can cause weird half-updated
data — a bug that would only show up occasionally and be really annoying
to track down later.

## Consequences

Because I'm storing everything in a plain Python dictionary in memory,
all of that tracking information disappears if the aggregator container
ever restarts in the middle of processing an order. Any order that was
mid-flight at that moment would just be lost, with no completion message
ever sent for it, complete or partial. For a real production system, I'd
want this state saved somewhere that survives a restart, like a small
database, instead of just living in memory.

The lock also means only one result can be processed at a time across the
whole aggregator, since everything routes through that one lock. For this
assignment's small scale that's totally fine, but if this had to handle a
huge amount of traffic, that single lock would become the bottleneck
slowing everything down, and I'd need a smarter way to let unrelated
orders be processed at the same time without stepping on each other.
